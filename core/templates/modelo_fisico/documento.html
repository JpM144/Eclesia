1. Información general

Motor: PostgreSQL {{ version.corta }}, versión leída del servidor {% if origen == "supabase" %}de Supabase{% else %}local{% endif %} ({{ version.larga }}).

Alojamiento: la base de trabajo es una instancia PostgreSQL local del proyecto Django. Se respalda en Supabase (PostgreSQL administrado) con el comando respaldar_supabase, que restaura la misma estructura y activa Row Level Security. Todas las tablas viven en el esquema public. Este documento se generó leyendo el catálogo de {% if origen == "supabase" %}Supabase{% else %}la base local{% endif %}, sin consultar filas de datos.

Convenciones de nombres

  • Tabla = app_modelo en minúsculas, sin separar las palabras del modelo (por ejemplo, sacramentos_primeracomunion).
  • Llave primaria: columna id de tipo identidad. Las tablas de detalle 1:1 de un sacramento (bautismo, confirmación, primera comunión, matrimonio y la nota marginal) usan como llave primaria la misma llave foránea a su tabla principal.
  • Llaves foráneas: terminan en _id y siempre apuntan a la columna id (o a la llave primaria) de la tabla referenciada.
  • Restricciones e índices: los que define el modelo llevan nombre propio (unico_…, libro_…); los que generan Django o PostgreSQL llevan la tabla, la columna y un sufijo: _pkey (llave primaria), _key o _uniq (único), _fk_… (foránea), _check y _like (índice para búsquedas con LIKE).

Django 5.2 crea las llaves foráneas como ON DELETE NO ACTION y DEFERRABLE INITIALLY DEFERRED; la regla de borrado del modelo (PROTECT, CASCADE, SET NULL) la aplica Django antes de borrar. El diccionario muestra las dos: la de la base y la del modelo.
